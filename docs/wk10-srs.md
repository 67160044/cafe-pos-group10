## 1. Introduction (บทนำและขอบเขต)

**วัตถุประสงค์:** ระบบ POS สำหรับร้านกาแฟหลายสาขา ช่วยรับออเดอร์และปรับแต่งเครื่องดื่ม คิดเงินและออกใบเสร็จ ส่งคิวไปยังบาร์เครื่องดื่มแบบเรียลไทม์ ตัดสต็อกตามสาขา จัดการสมาชิก Cafe Club และสรุปรายงานยอดขาย (รายละเอียดใน `wk03-requirements.md`)

**ขอบเขต (In Scope):** หน้าจอขายหน้าร้าน, ปรับแต่งเครื่องดื่ม, คิดเงิน (เงินสด/QR PromptPay แบบจำลอง), ใบเสร็จ, คิวบาร์ (KDS), ตัดสต็อกและแจ้งเตือนสต็อกต่ำ, ระบบสมาชิก, จัดการเมนู/สต็อก, ศูนย์ควบคุม HQ, รายงานยอดขาย และการควบคุมสิทธิ์ตามบทบาท

**นอกขอบเขต (Out of Scope):** แอปหรือตู้สั่งอาหารสำหรับลูกค้า, การเชื่อมต่อ Payment Gateway/EDC จริง (จำลองการชำระเงินเท่านั้น), การยื่นภาษีอัตโนมัติ, ระบบเดลิเวอรี่, การสั่งซื้อวัตถุดิบจากคู่ค้า, ฐานข้อมูลแยกภูมิภาค (จำลองหลายสาขาด้วย `branch_id` ในฐานข้อมูลเดียว)

**ศัพท์เฉพาะ:** POS (Point of Sale), KDS (Kitchen Display System หน้าจอคิวบาร์), RBAC (Role-Based Access Control), VAT 7%, Cafe Club (ระบบสมาชิก ส่วนลด 5% และสะสมแต้ม 1 แต้มต่อ 50 บาท)

## 2. Overall Description (ภาพรวมของระบบ)

**กลุ่มผู้ใช้งาน (System Actors)** ตาม `wk04-user-stories.md` และ Use Case Diagram (`images/wk04-use-case-diagram.png`):

| บทบาท | หน้าจอ | หน้าที่หลัก | ข้อจำกัดสิทธิ์ |
| --- | --- | --- | --- |
| Cashier (พนักงานหน้าร้าน) | `/order.html` | รับออเดอร์ ปรับแต่งเครื่องดื่ม ค้นหา/สมัครสมาชิก คิดเงิน ออกใบเสร็จ | ล็อกสาขาตามบัญชี |
| Barista (บาริสต้า) | `/barista.html` | รับคิว ปรุง และอัปเดตสถานะ 4 ขั้น | ล็อกสาขาตามบัญชี |
| Manager (ผู้จัดการร้าน) | `/menu.html`, `/report.html` | จัดการเมนู/สต็อก ดูรายงานยอดขาย | ดูได้ทุกสาขา |
| Super Admin HQ | `/admin.html` | จัดการพนักงาน (ยกเว้น Manager) สมาชิก/โปรโมชั่น และสาขา | ไม่มีสิทธิ์ดูรายงานยอดขาย |

ลูกค้าไม่ใช่ System Actor (ไม่มีบัญชีและไม่ล็อกอิน) ข้อมูลลูกค้าอยู่ในตาราง `member` เท่านั้น

**ข้อจำกัด (Constraints):** พัฒนาเป็น Web Application (Node.js/Express, Vanilla JS/CSS, MySQL) ใช้งานบนเบราว์เซอร์ของแท็บเล็ตหรือคอมพิวเตอร์ งบประมาณไม่เกิน 150,000 บาท และเวลา 3 เดือน

**สมมติฐาน:** รันเครื่องเดียว (Node.js 1 process และ MySQL 1 ตัว) เครือข่ายภายในร้านเสถียร และผู้ใช้เข้าสู่ระบบด้วยบัญชีที่ Admin สร้างไว้

## 3. Specific Requirements (ความต้องการของระบบ)

### 3.1 Functional Requirements

| รหัส | ข้อกำหนด (ย่อ) | ที่มา (Use Case / User Story) | สถานะ |
| --- | --- | --- | --- |

| FR-02 | คิดยอดรวม ส่วนลดสมาชิก 5% VAT 7% รองรับเงินสด (ปุ่มลัด คำนวณเงินทอน ป้องกันรับเงินไม่พอ) และ QR PromptPay ออกใบเสร็จ Thermal Slip | UC-01, US-02 | Implement แล้ว |
| FR-03 | ส่งออเดอร์ที่ชำระแล้วไปหน้าคิวบาร์ของสาขาเดียวกัน (เป้าหมายภายใน 2 วินาที) พร้อมเสียงเตือนและตัวจับเวลา | UC-02, US-03 | Implement แล้ว แต่ยังไม่ถึงเป้าหมายเวลา: หน้าคิวดึงข้อมูลทุก 3.5 วินาที จึงอาจแสดงช้าได้ถึง 3.5 วินาที และยังไม่ได้วัดเวลาจริง |

| FR-06 | ค้นหาสมาชิกด้วยเบอร์ 10 หลัก สมัครสมาชิกหน้าร้าน ใช้ส่วนลด และสะสมแต้มหลังขาย | UC-01 (4a), US-06 | Implement แล้ว |

### 3.2 Non-Functional Requirements

| รหัส | ประเภท | ข้อกำหนด |
| --- | --- | --- |
| NFR-01 | Performance | ออเดอร์ปรากฏหน้าคิวบาร์ภายใน 2 วินาที และ REST API ทั่วไปตอบภายใน 500 มิลลิวินาที (เป็นเป้าหมาย ยังไม่ได้วัดจริง และปัจจุบันหน้าคิวดึงข้อมูลทุก 3.5 วินาที ดู FR-03) |
| NFR-02 | Usability | ปุ่มสัมผัสไม่ต่ำกว่า 44x44 พิกเซล พนักงานที่ผ่านการอบรมไม่เกิน 10 นาทีทำรายการจนชำระเงินเสร็จได้ภายใน 60 วินาที (เป็นเป้าหมาย ยังไม่ได้จับเวลาจริง) |
| NFR-03 | Reliability | ข้อมูลสต็อกต้องถูกต้องแม้สั่งพร้อมกัน (ตรวจและตัดสต็อกใน transaction เดียว ห้ามติดลบ) |
| NFR-04 | Portability | แสดงผลถูกต้องบนแท็บเล็ต 10.1 นิ้วขึ้นไป (1280x800) และเบราว์เซอร์มาตรฐาน |
| NFR-05 | Security | ทุก API (ยกเว้น login และข้อมูลอ้างอิงสาขา/หมวดหมู่) ต้องแนบ token และตรวจบทบาท รหัสผ่านเก็บแบบ hash ไม่รับ token ทาง URL และจำกัดจำนวนครั้งที่ล็อกอินผิด (ปรับปรุงตามผลตรวจ `wk14-quality-review.md`) |
| NFR-06 | Data Integrity | ราคาในออเดอร์ต้องมาจากฐานข้อมูลฝั่งเซิร์ฟเวอร์เสมอ ห้ามรับราคาจาก client และการแก้/ลบข้อมูลต้องกรอง `branch_id` ป้องกันการเข้าถึงข้ามสาขา |

### 3.3 External Interface Requirements

- **User Interface:** 6 หน้าจอ (`login`, `order`, `barista`, `menu`, `report`, `admin`) ตามเอกสาร [Wireframe](wk10-wireframe.docx) และ [Input/Output Design](wk10-input-output-design.docx)
- **การชำระเงิน:** จำลองเงินสดและ QR PromptPay ไม่เชื่อมต่อผู้ให้บริการจริง
- **API:** REST ภายใต้ `/api/auth`, `/api/menu`, `/api/orders`, `/api/members`, `/api/reports`, `/api/admin` รูปแบบ JSON ชื่อ field แบบ camelCase สำหรับเมนูและรายงาน (endpoint อื่นยังเป็น snake_case ดู `wk14-quality-review.md` รหัส B1)

### 3.4 Data Requirements

เอนทิตีหลักและความสัมพันธ์ตามฐานข้อมูลที่ใช้งานจริง (`schema.sql` ใน repository โค้ด) ซึ่งขยายจาก ER Diagram และ `wk07-schema.sql` ที่ส่งใน wk07 (ความต่างและเหตุผลดูข้อ 4):

| ตาราง | สาระสำคัญ |
| --- | --- |
| `branch`, `category` | ข้อมูลสาขาและหมวดหมู่เมนู |
| `user` | บัญชีพนักงาน (email ไม่ซ้ำ, role: admin/manager/cashier/barista, สังกัด `branch_id`) |
| `menu_item` | เมนูแยกตามสาขา (ราคา, `stock_quantity`) |
| `member` | สมาชิก Cafe Club (เบอร์โทรไม่ซ้ำ, แต้ม, `discount_rate`) |
| `orders`, `order_item` | หัวบิล (สาขา, ผู้ขาย, สมาชิก, วิธีชำระ, สถานะ 5 ค่า) และรายการ (จำนวน, ราคา ณ ตอนขาย, หมายเหตุ) |
| `stock_movement` | ประวัติการตัดสต็อกจากการขาย |
